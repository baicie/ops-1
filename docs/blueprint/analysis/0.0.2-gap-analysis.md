# OpsWeave 0.0.2 Data Foundation — Gap Analysis

- **基线**: `v0.0.1-dev.1` / `4ce130b`
- **开发分支**: `feat/0.0.2-data-foundation`
- **分析日期**: 2026-10-22
- **结论**: 0.0.1 的插件安装、签名、部署、激活、Gateway、审计和 Web Extension 可以复用；0.0.2 所需的 **Capability Fabric 调用身份**、**插件存储所有权**、**Data Catalog/Integration 契约与实现**尚未存在，必须在 Phase A 先定义。

> 本文件只陈述已阅读源码与契约后的事实，不把蓝图中的设计声明当成已实现能力。

## 2. 已实现且可复用的能力

| 能力 | 实际实现 | 对 0.0.2 的复用方式 |
|---|---|---|
| 插件包与签名 | `plugin_packages`、Ed25519 bundle 签名、digest/版本冲突拒绝 | Catalog/Integration 继续用同一 bundle 工具链 |
| 安装/部署/激活/禁用/升级/回滚 | `deployments.rs` 的 activation revision、desired/observed、placement、receipts | 两个业务插件独立安装、独立版本、独立部署 |
| Manifest v1.1 | `ManifestV11`、`provides/requires`、前端 contributions、资源预算 | 保留 1.1 读取；新字段必须采用新 schema 版本或旁路契约 |
| Capability 注册（静态） | `capability_registrations` 保存 provides/requires；`validate_requires()` 在激活时检查 active provider | 扩展为可解析/可授权/可撤销的 Capability Registry |
| Gateway（用户流量） | `gateway::proxy` 按 plugin 路由，校验 API prefix、READY 实例、节点 endpoint 策略、超时、GET 重试 | 作为同步 Capability 调用的承载层，不另建 RPC 框架 |
| RBAC/会话 | 用户 session、admin/operator/viewer、CSRF、审计 | 业务 API 继续使用用户身份；插件间调用必须新增 workload 身份 |
| Web Extension Host | `extensions.tsx` 动态加载 UMD、host React、导航/路由、错误边界、host.api 代理 | Catalog/Integration 两个前端扩展直接接入 |
| Node Runtime | Docker OCI、readiness/liveness、数据代理、quarantine、lease | 插件容器运行方式不变 |
| 审计与回执 | `audit_events`、`operation_receipts` | Capability 调用、IngestionRun、Schema Publish 追加审计/回执 |
| 契约校验 | JSON Schema + OpenAPI + Python validator + runtime conformance | Phase A 新契约加入同一可执行检查链 |

## 3. 已定义但未实现的能力

| 蓝图/任务要求 | 现状 | Gap |
|---|---|---|
| Capability 逻辑发现与选择 | 只有 `provides/requires` 注册和 `validate_requires` | 无 Capability resolution endpoint、provider selection policy、optional dependency、版本区间/不兼容拒绝 |
| Capability Grant/Revoke | `permissions` 只是 manifest 字符串；没有 grant 表/API | 无运行时授权，不能把 manifest metadata 当作权限 |
| 插件调用身份 | Gateway 只接受用户 session；Node proxy 转发用户相关 header | 无 workload identity、无签名 caller context、无服务端 scope 校验 |
| 插件专用数据库 Schema | 只有 `kernel.plugin_migrations` 表，且没有代码使用 | 无 schema/role 创建、无最小权限身份、无连接凭据注入 |
| Migration version/checksum | 表结构存在但无 migration plan、准入、锁、执行器 | 无法阻止未经审查的迁移；无 expand/migrate/contract 门禁 |
| Data Catalog 对象/API | 无 Dataset/Schema/Revision/Lineage 表、无 OpenAPI | Phase A 契约与 Phase B 存储全部缺失 |
| Data Integration 对象/API | 无 Source/Connector/Preview/IngestionRun 表、无 OpenAPI | Phase A 契约与 Phase B 存储全部缺失 |
| 跨插件 Capability 调用 | 无 capability endpoint；只有按 plugin 的 `/api/v1/gateway/{plugin_id}` | Integration 无法以自身身份调用 Catalog，也无法验证调用者 |
| SSRF/secret redaction | Node 有 endpoint allowlist；Data Integration 尚无 HTTP connector | 需新增 DNS/redirect/private IP/响应大小/脱敏防护 |
| Data UI | Web Shell 有扩展机制，无 Catalog/Integration 页面 | 需两个独立 remote extension |
| Golden Path | 无 Data 插件、无真实跨插件链路 | 需真实容器 + PostgreSQL + Gateway 验收 |

## 4. 当前契约缺失

### 4.1 Capability Fabric

现有 `CapabilityRef` 只有 `name` 和 `major`，不足以表达：

- capability identity（provider + name + major + contract digest）；
- required/optional；
- 版本范围、兼容/拒绝规则；
- provider selection（default/specified/least-loaded 等）；
- grant/revoke、scope、调用预算和超时；
- caller workload identity 和 audience；
- 依赖方 disable 保护；
- `CAPABILITY_UNAVAILABLE`、`CAPABILITY_FORBIDDEN`、`CAPABILITY_TIMEOUT` 等稳定错误。

Phase A 需新增可验证的 Capability OpenAPI/JSON Schema，并在 Manifest 侧采用兼容扩展。**不能把现有 `permissions` 字段直接当成运行时 grant。**

### 4.2 Data Catalog

缺少 Dataset、SchemaDefinition、FieldDefinition、ModelRevision、EntityType、DatasetWriteRequest/Receipt、Schema Compatibility、DataLineage 的正式 Schema 和 OpenAPI。

需要明确：

- 字段类型集合、nullable、default、semantic tags；
- Schema digest 的规范化算法；
- 不可变 revision 与 draft/publish 的状态机；
- 兼容规则（新增 nullable 字段允许；删除/改类型/新增 required 拒绝）；
- `SchemaConflict`、`SCHEMA_REVISION_IMMUTABLE` 等错误；
- 写入的 `Idempotency-Key`、request digest、accepted/rejected/unknown 计数；
- Catalog 的存储适配器边界和容量/留存限制。

### 4.3 Data Integration

缺少 DataSource、ConnectorType、CredentialReference、ConnectionTest、SourceSnapshot、FieldDiscovery、PreviewRequest/Result、FieldMapping、IngestionSpec、IngestionRun、QualityResult、Batch Lineage 的正式契约。

需要明确：

- `sourceBatchKey` 的稳定生成规则和唯一约束；
- preview 的只读保证、最大样本数/字节数/超时；
- HTTP connector 的 SSRF 策略：scheme、DNS 解析后 IP、redirect、IPv4/IPv6、loopback/link-local/metadata、响应大小；
- secret reference 只存引用，不返回明文；日志/错误脱敏；
- `UNKNOWN` 只在外部写入结果不可判定时使用，不能自动换幂等键重试；
- `data.source.v1` 的边界（本版本只作为 Integration 的 capability，不提前实现通用 source 平台）。

### 4.4 插件存储

Manifest v1.1 没有 storage/migration 节；`plugin_migrations` 仅有表。Phase A 必须新增：

- `storage` 声明（schema name、migration plan digest、retention）；
- Kernel 创建 schema/role 的输入输出和失败语义；
- migration id/checksum/status、expand/migrate/contract 阶段；
- 禁止插件访问 `kernel.*` 或其他插件 schema 的数据库授权模型；
- 禁用/卸载默认保留数据，purge 独立高权限并需备份确认；
- 哪些迁移不可自动回滚（必须明确拒绝而不是假装回滚）。

## 5. 需要补充的数据库与 API

### 5.1 数据库（建议最小集）

| 表 | 所有者 | 用途 |
|---|---|---|
| `kernel.capability_grants` | Kernel | provider/consumer/name/major/scope/state/expiry |
| `kernel.plugin_storage_bindings` | Kernel | plugin schema、role、secret reference、state |
| `kernel.plugin_migrations` | Kernel | 现有表补齐 checksum/phase/plan digest/执行记录 |
| `catalog.datasets` | Catalog | Dataset 语义与 owner |
| `catalog.schema_revisions` | Catalog | 不可变 revision、digest、兼容性结果 |
| `catalog.schema_fields` | Catalog | 字段定义/顺序/类型/default |
| `catalog.dataset_records` | Catalog | 首版受限小规模存储 |
| `catalog.dataset_receipts` | Catalog | 幂等写入回执 |
| `catalog.lineage_batches` | Catalog | 批次级来源 |
| `integration.sources` | Integration | Source、endpoint ref、credential ref、status |
| `integration.source_snapshots` | Integration | 发现/预览快照摘要 |
| `integration.ingestion_specs` | Integration | source/schema pin、mapping、target |
| `integration.ingestion_runs` | Integration | run 状态、计数、错误、UNKNOWN |
| `integration.run_batches` | Integration | sourceBatchKey、lineage、quality |

> 具体 schema 名在 Phase A ADR 中冻结；不得让业务插件直接读写 `kernel.*`。

### 5.2 API

- Kernel: Capability resolve/list/grant/revoke、migration plan/inspect、plugin storage status。
- Catalog: datasets CRUD、schema draft/publish/diff、dataset records write/read、lineage。
- Integration: sources、connection-test、discover、preview、mappings、ingestion-specs、runs、quality。
- Capability endpoint: 同步调用，必须带 workload caller context；不能复用用户 session 绕过。
- 所有写 API：明确 `Idempotency-Key`、request digest、409 冲突、超时/UNKNOWN。

## 6. 可能破坏 0.0.1 兼容性的改动

| 改动 | 风险 | 建议 |
|---|---|---|
| 在 Manifest v1.1 增加字段 | Rust `deny_unknown_fields` 和 JSON Schema `additionalProperties:false` 会使旧 Kernel 拒绝新包 | 不修改 1.1；新增 1.2 schema/reader，0.0.2 Kernel 同时读 1.1/1.2；旧插件保持 1.1 |
| 改变 Gateway 认证 | 现有用户 Gateway 直接透传 caller headers | 新增独立 capability endpoint/workload token；不改变用户 gateway 语义 |
| 插件数据库凭据注入 | 可能泄漏到日志、DesiredState、容器 env | 只注入短期/最小权限凭据；日志/API 永不返回明文；生产需 KMS/secret manager |
| Capability registration 唯一约束 | 现有 `(plugin_id, revision_id, direction, name)` 不允许同名不同 major | 迁移前先做回填/唯一键调整，避免破坏旧包 |
| Disable 默认行为 | 现有 disable 不检查反向依赖 | 新依赖检查必须只阻止 *required* 依赖；显式 force 需高权限并审计 |
| Migration 执行 | 自动回滚承诺可能破坏数据 | 不做通用自动回滚；失败进入 BLOCKED/人工恢复 |
| 前端 SDK | 旧 remote 只拿到 get/post | 只增加向后兼容方法；不改旧 `host.api` 形状 |

## 7. 安全与故障语义风险

1. **身份伪造**: 任何 `X-OpsWeave-*` 身份 header 都不能作为信任根；必须由 Kernel 签发并验证 audience/scope/expiry。
2. **Capability 绕过**: 插件容器不能直接访问其他插件端口或数据库；必须只允许经过 Gateway/Node 代理的 capability 调用。
3. **SSRF**: HTTP/JSON connector 必须解析并校验 IP，阻止 loopback/link-local/private/metadata、DNS rebinding、重定向和超大响应；预览与 ingestion 使用同一策略。
4. **秘密泄漏**: CredentialReference 只返回引用；错误、日志、审计、前端不得出现明文密码/Token。
5. **幂等性**: Catalog 写入与 IngestionRun 必须有唯一键和 request digest；网络超时返回 `UNKNOWN`，禁止自动生成新键重试。
6. **迁移**: 破坏性 migration 需显式 maintenance/审批；失败不能把旧 revision 标记为可安全回滚。
7. **Schema 兼容**: 只有 additive nullable 等规则可自动兼容；不兼容变更必须拒绝并返回 diff。
8. **Disable 依赖**: Catalog 被 Integration required 依赖时必须拒绝 disable；恢复/回滚要重新检查依赖。
9. **数据保留**: disable/uninstall 默认保留数据；purge 是单独高权限且需备份确认。
10. **容量**: 首版 Catalog 只支持小规模存储，必须公开行数/字节/留存上限，不能暗示通用数据仓库能力。

## 8. D00–D07 映射与实施顺序

| 阶段 | 本 Gap Analysis 后的动作 | Gate |
|---|---|---|
| D00 | Capability Fabric + storage/migration + Data Catalog/Integration 契约 | schema/OpenAPI/negative tests 全绿 |
| D01 | Catalog PostgreSQL schema、migration、API、幂等写入 | Dataset/Schema revision 兼容测试 |
| D02 | Catalog Web Extension | 列表/详情/Editor/Diff/Lineage；明暗/响应式 |
| D03 | Integration HTTP/JSON connector、SSRF、secret ref、preview | 真实 HTTP 服务 + SSRF 负测 |
| D04 | Integration Web Extension | Wizard/Discovery/Preview/Mapping |
| D05 | Source→Parse→Map→Validate→Catalog Sink | 真实跨插件、幂等、UNKNOWN |
| D06 | Quality/Run history/lineage | 计数、脱敏错误、保留 |
| D07 | 真实双插件安装 + Golden Path + 0.0.1 回归 | 独立部署、disable 保护、恢复 |

## 9. 最小假设（Phase A 前）

- 继续使用 `http-json-v1`；Capability 同步调用复用 Kernel Gateway/Node proxy，不引入消息总线或 gRPC。
- 0.0.2 新包可以使用新的 Manifest schema 版本；0.0.1 的 1.1 包仍可安装/运行。具体版本号在 Phase A ADR 冻结。
- 首版 Catalog 使用 **插件专属 PostgreSQL schema + 受限小规模数据表**，不实现物理表自动映射、CDC、增量水位或通用 DAG。
- 首版 Integration 只实现 HTTP/JSON（含受限样本文件），不做 Zabbix。
- 本地开发仍使用两个 Node 进程共享 Docker daemon；生产 Linux/mTLS/Fencing/OCI 供应链不作为 0.0.2 的已完成项。
- 没有用户批准前不创建生产数据库凭据、不把开发 secret 提交到仓库。

## 10. 结论

0.0.1 的可复用面足够支撑 0.0.2，但 **不能直接在现有 Gateway 上加两个业务插件**：

1. 先补 Capability workload identity + grant/revoke；
2. 先补插件 storage ownership/migration gate；
3. 先定义并测试 Data Catalog/Integration 的可执行契约；
4. 再实现两个独立插件和真实 Golden Path。

在上述契约与迁移门禁完成前，不进入业务插件实现。
