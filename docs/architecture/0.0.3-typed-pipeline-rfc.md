# RFC: 0.0.3 Typed Pipeline Runtime + Durable Job Worker

Status: **DRAFT — implementation BLOCKED by version gate**  
Date: 2026-10-23  
Scope gate: [00-roadmap-and-scope-gates.md](../blueprint/plan/00-roadmap-and-scope-gates.md)  
Related: [Data Foundation 0.0.2](../blueprint/07-data-foundation-002.md), [Future Workflow](../blueprint/08-future-workflow-observability-ai.md)

## 1. Decision Summary

0.0.3 adds a **closed, typed pipeline IR** and a **durable, fenced job runtime** on the existing Kernel, PostgreSQL, Node runtime and Capability Gateway. It does not add arbitrary user code, a second scheduler, a generic distributed DAG optimizer, an AI agent, an OTLP row pipeline, or a full visual editor.

The implementation may not start on `main` until PR #1 (0.0.2) is merged and the 0.0.3 branch is cut from the updated `main`. This RFC and the contract files are a design draft; no runtime implementation is included here.

## 2. Goals

1. Versioned, immutable Pipeline IR with canonical digest.
2. Typed input/output ports and deterministic static type checking.
3. DAG acyclicity, bounded node/edge/data sizes, deterministic topological order.
4. A finite Node Registry: Source, Parse, Map, Filter, Validate, Sink.
5. Durable Job state in PostgreSQL with attempts, lease, fencing token and checkpoint.
6. Strict single-execution eligibility at every external side-effect boundary.
7. Recover after Worker or Kernel restart without duplicating committed side effects.
8. Audit/status/log records for Pipeline, Revision, Run, Job, Attempt, Lease and Checkpoint.

## 3. Non-goals

- arbitrary JavaScript, Python, shell or WASM execution;
- arbitrary external HTTP from a pipeline node;
- generic multi-tenant distributed DAG scheduling/optimization;
- at-least-once execution without a fenced sink;
- a visual graph editor (0.0.4);
- OTel high-frequency data through the workflow executor (0.0.6);
- pretending that a stale lease means the old worker has stopped.

## 4. Core Model

### 4.1 PipelineDefinition and PipelineRevision

`PipelineDefinition` is an immutable, content-addressed document. A `PipelineRevision` publishes one definition:

```text
PipelineDefinition (draft input)
  -> static validation
  -> canonical JSON + sha256 digest
  -> PipelineRevision (PUBLISHED, immutable)
  -> PipelineExecutionPlan (derived, deterministic)
  -> Job (pins pipelineId + revision + digest)
```

A Job never references "latest". A published revision cannot be mutated; changing any node, edge, port, config or bound creates a new revision. The digest is computed over canonical JSON (sorted object keys, no insignificant whitespace) and excludes the digest field itself. The exact canonicalization algorithm is part of the implementation contract and must be tested cross-language.

### 4.2 Node Registry

Only built-in registry entries are executable. Each entry declares:

- `type` and `typeVersion`;
- typed input/output ports;
- `execution` (`PURE` or `BOUNDED_IO`);
- input/output record limits.

Unknown type/version, duplicate node IDs, duplicate output ports or a port mismatch is a hard rejection. User code and arbitrary HTTP cannot be registered as a node type in 0.0.3.

### 4.3 Ports and Type Compatibility

Types are deliberately small: `string`, `integer`, `number`, `boolean`, `timestamp`, `json`, `dataset_ref`. An edge is valid only when:

1. source node and port exist;
2. target node and port exist;
3. the edge `dataType` equals both port types;
4. a target required input has exactly one incoming edge;
5. schema revision pins, when present, are compatible;
6. source has no incoming requirement violations and sink has no outputs.

No implicit `any`, no implicit string-to-json coercion and no runtime-only edge acceptance.

### 4.4 DAG and Determinism

- Maximum 64 nodes and 128 edges.
- Maximum input records 10,000 per run, maximum checkpoint state 1 MiB, maximum output bytes 8 MiB for the first bounded implementation (configurable only within hard server bounds).
- Kahn topological sort; ready nodes ordered lexicographically by `nodeId`; the resulting order is persisted in `PipelineExecutionPlan.orderedNodes`.
- Cycles, unknown endpoints, duplicate IDs and missing required inputs reject publication.
- The same canonical revision and limits always produce the same plan digest.

## 5. Job Lifecycle

```text
QUEUED --claim--> CLAIMED --start--> RUNNING --result--> SUCCEEDED
   |                  |                  |
   |                  +--lease expiry----+--> QUEUED (retry, new fence)
   |                  +--cancel----------> CANCELLED
   +--cancel-----------------------------> CANCELLED
RUNNING --failure--> FAILED --retry (if attempts remain)--> QUEUED
```

Every transition is persisted in PostgreSQL with a compare-and-set precondition. `SUCCEEDED` and `CANCELLED` are terminal. A retry creates a new attempt and a new lease/fencing sequence; it never reuses the old lease.

### 5.1 Lease and Fencing

`JobLease` contains worker identity, `leaseId`, `expiresAt`, heartbeat and a `FencingToken` with a monotonically increasing `sequence`. Claim increments the sequence in the same database transaction that changes `QUEUED -> CLAIMED`.

Rules:

- only the current non-expired lease with the highest sequence may heartbeat, checkpoint, or submit a result;
- lease expiration alone does **not** prove the old worker stopped; it only makes a new claim possible;
- every external side effect (Catalog write, file/object write, webhook, etc.) must pass the current fence to the sink boundary or use a sink idempotency key tied to `(jobId, attempt, checkpointSequence)`;
- an old worker presenting a stale sequence receives `409 STALE_FENCE`; its side effect must be rejected before commit;
- fencing tokens are signed/opaque server-issued values; the sequence is not trusted from the worker.

### 5.2 Duplicate claim and duplicate submission

Claim uses `SELECT ... FOR UPDATE`/CAS on the Job row. The winner gets the lease; losers get `409`. Submission uses the same fencing check and a unique result key `(jobId, fenceSequence)`. Duplicate submission with the same fence and same result digest returns the original result; a different digest is a conflict.

### 5.3 Checkpoints

A checkpoint records `checkpointId`, `jobId`, `attemptNumber`, monotonic `sequence`, `fencingSequence`, `inputCursor`, `stateDigest`, `createdAt`. Only the current fence may append. A recovery worker starts from the latest checkpoint whose fence is not superseded; it must not replay already committed external effects. Checkpoints are bounded and content-addressed; they are not a general event log.

### 5.4 Kernel restart

Pipeline revisions and Job state live in PostgreSQL. After Kernel restart:

- `QUEUED` jobs remain claimable;
- `CLAIMED/RUNNING` jobs whose lease expired are recoverable through a new claim and higher fence;
- a worker with an old boot ID cannot resume by self-assertion; it must re-claim and receive the new fence;
- in-flight process-local state is never assumed durable; only checkpoints and committed external effects survive.

## 6. Execution Boundary

```text
Kernel API
  -> authorization + audit
  -> Pipeline validation / revision publish
  -> Job store + lease/fence
  -> Node worker (bounded built-ins only)
  -> fenced Sink adapter
  -> Catalog capability / existing Dataset storage
```

The worker is not a second identity or deployment system. It uses the existing Node enrollment, instance identity, workload token and Capability Gateway authorization. A worker cannot access Docker socket, host files, or another tenant's data.

## 7. Security Boundaries

- All pipeline and job mutations require existing Kernel scopes; no dev bypass.
- The worker must present its Node instance identity and workload token; a pipeline job does not grant arbitrary capability scopes.
- Sink writes require the current fence at the actual side-effect boundary.
- Pipeline config is data, not code; no arbitrary URL fetch unless an approved bounded Source connector type exists.
- Error messages are redacted; logs carry IDs and digests, not secrets.
- Audit events: `pipeline.created`, `pipeline.validated`, `pipeline.revision_published`, `job.submitted`, `job.claimed`, `job.lease_expired`, `job.checkpointed`, `job.succeeded`, `job.failed`, `job.cancelled`, `job.stale_fence_rejected`.

## 8. Persistence and Concurrency

Suggested PostgreSQL tables (implementation gate):

- `pipeline.pipeline_definitions` — canonical document, digest unique;
- `pipeline.pipeline_revisions` — `(pipeline_id, revision)` unique, immutable;
- `pipeline.pipeline_plans` — derived plan + plan digest;
- `pipeline.jobs` — state, current fence sequence, idempotency key unique;
- `pipeline.job_attempts` — attempt history;
- `pipeline.job_leases` — current and historical leases;
- `pipeline.job_checkpoints` — append-only, sequence unique per attempt;
- `pipeline.job_results` — unique `(job_id, fence_sequence)`;
- `pipeline.job_events` — audit/status transition log.

All job status changes and fencing checks use one transaction with `SELECT ... FOR UPDATE` or optimistic CAS. External side effects are never in the same transaction as the state transition; they are protected by an idempotency key and fence check at the boundary.

## 9. Failure Classification

| Code | Meaning | Retry |
|---|---|---|
| `PIPELINE_INVALID` | static validation failed | no |
| `PIPELINE_REVISION_NOT_FOUND` | pinned revision missing | no |
| `JOB_IDEMPOTENCY_CONFLICT` | same key/different input | no |
| `JOB_ALREADY_CLAIMED` | valid competing claim | no |
| `JOB_LEASE_EXPIRED` | current worker lease expired | new claim only |
| `STALE_FENCE` | old worker/fence | no; reject side effect |
| `JOB_TIMEOUT` | bounded execution exceeded | retry policy |
| `NODE_EXECUTION_FAILED` | deterministic node error | retry policy |
| `SINK_UNAVAILABLE` | external sink unavailable | retry policy |
| `CANCELLED` | cancellation accepted | no |

`UNKNOWN` is reserved for a side-effect outcome that cannot be proven committed or absent. It must never be silently treated as success or automatically replayed.

## 10. Versioning and Compatibility

- IR `schemaVersion`: `pipeline.opsweave.io/v1`.
- Node registry entries are type+version; a revision pins both.
- A node version bump is a new registry entry; old published revisions remain readable/executable if their node version is still registered.
- Breaking IR changes require a new major and a migration/refusal ADR.
- Jobs pin the revision digest; they do not silently follow newer revisions.

## 11. Acceptance Plan

P0 contract checks (this draft):
- JSON Schema validation of PipelineDefinition, revision, plan, Job, lease, checkpoint.
- DAG/type/cycle/unknown-node/limit/state-transition/fencing conformance tests.
- OpenAPI operation and fencing-header presence checks.

Implementation acceptance (after Gate):
1. valid DAG executes through Source→Parse→Map→Filter→Validate→Sink;
2. type mismatch rejects;
3. cycle rejects;
4. unknown node type rejects;
5. resource limits reject;
6. worker crash while RUNNING;
7. lease expiry and another worker takeover;
8. stale fence result rejected;
9. Kernel restart recovery;
10. same idempotency key does not duplicate a row or side effect.

PostgreSQL atomicity of state transitions and cross-system sink idempotency are tested separately. A database rollback test cannot prove a sink did not double-write.
