# 0.0.3 Fenced Sink and Data Catalog Compatibility

Status: **BLOCKED for runtime integration**  
Date: 2026-10-23  
Related: RFC 0.0.3, ADR-013, `contracts/schema/sink-receipt.v1.schema.json`

## Decision

The existing `data.catalog.v1` `POST /datasets/{id}/records` operation has an
idempotent `sourceBatchKey`, but it has **no Job/Fence identity and no
transactional relationship with `pipeline.job_leases`**. It therefore cannot
prove the required invariant:

> A worker whose lease was superseded cannot commit a Dataset side effect.

A Kernel-side check followed by a Catalog write is a TOCTOU check and is not
acceptable.

### Stable effect identity

```text
effectId = "efx:" + sha256(canonical_json({
  jobId, pipelineId, pipelineRevision, sinkNodeId, logicalBatchId
}))
```

`attemptNumber` and `fencingSequence` are deliberately absent. A retry or a
takeover must reuse the same `effectId`. A different logical batch is a
different effect. Same `effectId` + same request digest returns the original
receipt; same `effectId` + different digest is `IDEMPOTENCY_CONFLICT`. This
prevents an old attempt that committed before its response was lost from being
re-executed after a takeover. The runtime integration is therefore **BLOCKED** until the Catalog
implementation below exists and a real E2E test proves the boundary. No Mock
Sink is accepted as final evidence.

## Required extension (additive, same capability major)

Add an optional operation to the existing `data.catalog.v1` capability:

```http
POST /api/v1/capability/data.catalog.v1/datasets/{datasetId}/fenced-records
X-OpsWeave-Fencing: <signed fence token>
Content-Type: application/json
```

Request:

```json
{
  "schemaRevision": 1,
  "sourceBatchKey": "job-<uuid>-attempt-1-fence-7",
  "fence": {
    "jobId": "uuid",
    "leaseId": "uuid",
    "fencingSequence": 7,
    "sinkScope": "dataset:host-metrics:revision:1",
    "expiresAt": "2026-10-23T00:05:01Z",
    "signature": "ed25519:..."
  },
  "records": [ ... ]
}
```

Response: `SinkReceipt` (`sink-receipt.opsweave.io/v1`) with `COMMITTED`,
`REJECTED`, or `UNKNOWN`. A `GET /datasets/{id}/receipts/{sourceBatchKey}` is
required for UNKNOWN recovery.

Existing `POST /datasets/{id}/records` remains unchanged for 0.0.2 clients.
The new endpoint is only additive; old clients and old plugin versions continue
to work. The capability major remains `v1`; clients must feature-detect the
operation, not assume it exists.

## Fence issuance and generation

1. The Kernel JobStore claim transaction changes `QUEUED -> CLAIMED`, creates a
   lease and increments the job's `fence_sequence` in the same PostgreSQL
   transaction.
2. Kernel signs the token with its fence signing key. The token binds at least
   `jobId`, `leaseId`, `fencingSequence`, `sinkScope`, `issuedAt`, `expiresAt`,
   and `keyId`. Workers never mint or extend a token.
3. A new claim always gets a strictly greater sequence. A retry is a new
   attempt and a new token; the old token is never reissued.
4. The Catalog verifies the signature and `expiresAt` locally; it never trusts
   worker-supplied sequence fields without the signature.

## Atomic boundary

The only acceptable commit boundary is the Catalog's own PostgreSQL
transaction:

```text
BEGIN
  verify signed fence (local public key, expiry, scope)
  INSERT INTO catalog_fenced_receipts (
    job_id, fencing_sequence, source_batch_key, request_digest,
    dataset_id, schema_revision, status, committed_at
  ) ... ON CONFLICT (job_id, fencing_sequence) ...;
  INSERT records ... (same transaction);
  INSERT lineage ... (same transaction);
COMMIT
```

Unique constraints:

- `(job_id, fencing_sequence)` — one accepted fence write;
- `(dataset_id, source_batch_key)` — stable idempotent batch;
- receipt stores the request digest; same key + different digest is
  `IDEMPOTENCY_CONFLICT`.

A stale worker cannot commit after a newer fence is recorded because the
Catalog transaction rejects a lower sequence and the unique constraint blocks a
duplicate. The Kernel result API also rejects a stale fence, but that is not
sufficient by itself.

## Reservation issue (why this is BLOCKED)

Catalog and the Kernel JobStore are separate PostgreSQL schemas/connections.
The following remains possible without a reservation protocol:

```text
old worker: verify old fence (valid) -> Catalog write
new worker: claim newer fence -> Catalog write
```

If the old write commits after the new claim but before the new write, the
Catalog high-water mark has not yet seen the new sequence. A simple
`sequence > high_water` check is therefore not enough.

The proposed completion is a Kernel-side **SinkReservation**:

1. Worker requests a short-lived sink grant for its current fence.
2. Kernel transaction marks the job `SINK_RESERVED`, blocking a new claim until
   the grant is completed or expired.
3. Catalog accepts at most one receipt for that grant and commits records +
   receipt atomically.
4. Worker reports the receipt to Kernel; Kernel clears the reservation and
   completes the result. A crash lets the reservation expire; a new claim is
   allowed only after expiry and must use a higher fence.

Even this requires a careful proof of the expiry/commit race boundary. Until
the Catalog and Kernel implement and test it, the status is **BLOCKED**. A
Kernel-only fence check plus an unprotected Catalog write must never be
recorded as PASS.

## Retry and UNKNOWN rules

- Stable sink identity: `sourceBatchKey = f(jobId, attempt, fenceSequence)`.
- Same fence + same request digest returns the existing receipt.
- Same fence + different digest -> `IDEMPOTENCY_CONFLICT`.
- Different fence after a committed receipt -> `STALE_FENCE` (the write is
  already committed once; do not duplicate).
- If the worker times out before receiving a response, it must query the
  receipt by `sourceBatchKey`; a `COMMITTED` receipt means success.
- If no receipt exists and the outcome is not provable, return `UNKNOWN`; do
  not invent success and do not auto-replay with a new key.

## Compatibility and migration

- Additive optional route in `data.catalog.v1`, no change to old `/records`.
- New tables are in the plugin schema; Kernel does not read plugin tables.
- A 0.0.3 Catalog plugin release must be independently versioned and tested
  against a 0.0.2 Integration client.
- The new operation is only enabled when the plugin advertises the
  `fenced-records` capability feature; clients must not assume it.

## Required real E2E before PASS

1. old worker's fenced write after a new claim -> `409 STALE_FENCE`;
2. new worker commits exactly once;
3. duplicate submission with the same fence/key -> same receipt, one row;
4. duplicate key/different digest -> `409 IDEMPOTENCY_CONFLICT`;
5. timeout then receipt lookup -> no duplicate;
6. Catalog unavailable -> `UNKNOWN`, never treated as success;
7. 0.0.2 client on `/records` still passes.
