## 2. Milestone A — Live Catalog: PASS

### Service identity

- New service principal `opsweave.kernel.catalog`.
- Migration grants only `dataset:read` on `data.catalog.v1`.
- Grant is still resolved through the normal Capability provider routing, grant state,
  scope matching and provider binding.
- No browser admin session, Node control credential, plugin private table or
  hard-coded Catalog token is used.
- Kernel mints a short-lived workload token for this service principal and calls its
  own Capability endpoint; Catalog sees a normal workload caller context.
- Catalog metadata calls are audited as `capability.service_invoke`.

### Publish-time schema pin

`POST /api/v1/pipelines` and revision publish now:

1. parse Sink `datasetId` as UUID;
2. call live `GET /api/data-catalog/datasets/{uuid}` via Capability;
3. call live `GET /api/data-catalog/datasets/{uuid}/schemas`;
4. require the requested revision to exist and be `PUBLISHED`;
5. recompute the schema digest from fields and compare it with Catalog's digest;
6. pin `schemaRevision` and `schemaDigest` into the immutable sink config;
7. then generate the revision digest and ExecutionPlan.

The static `contracts/examples/schema-catalog.json` is now `#[cfg(test)]` only and
is not reachable from production publish.

Worker verifies the pinned schema revision and digest through Catalog before Sink.

## 3. Milestone B — Node-managed Worker

`POST /internal/v1/pipeline-jobs/claim-next` now selects:

- `QUEUED` jobs;
- `CLAIMED` jobs without an active lease;
- `RUNNING` jobs without an active lease;
- excludes attempts-exhausted jobs and active leases.

The actual mutation still flows through the existing atomic `claim_job` CAS.
Candidate selection and claim are not yet in one transaction, so concurrent
discovery can return a harmless conflict rather than blocking; this is why
Atomic Claim-Next is `PARTIAL`.

Node supervisor now:

- stops the current worker when the enable marker is removed;
- stops on quarantine;
- stops when the bound instance is no longer READY;
- uses bounded exponential backoff for repeated failures;
- reaps the child with `kill_on_drop` and explicit kill on shutdown.

Worker heartbeats before each batch rather than on an independent timer;
continuous long-running heartbeat coverage is therefore `PARTIAL`.
