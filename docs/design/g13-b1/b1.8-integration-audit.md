## 2. Phase 1 — Evidence vs Human Verdict

### 复现（真实 PostgreSQL 17，确定性状态而非 sleep）

`incidents::effect_tests::automation_evidence_cannot_commit_after_a_human_verdict`：
1. fixture incident OPEN，job RUNNING 且持有效 lease；
2. 人工 verdict（INCONCLUSIVE）先提交，incident 变 CONCLUDED；
3. 以 automation actor 调用 Evidence 写入器（模拟“外层 OPEN 检查已通过、verdict 后恢复写入”的交错）。

修复前结果：写入成功，返回 `(true, EvidenceView { after_verdict: true, verified_trust: SOURCE_ATTESTED, ... })`，Evidence 行落库；Verdict 的 `considered_evidence_count` 不包含它。**CONFIRMED**。

### 根因

`append_automation_evidence` 的状态检查在事务外；`insert_evidence_as` 事务内第二次读状态后只拒绝 `CLOSED`，不拒绝 `CONCLUDED`，且没有行锁。`UPDATE incidents ... WHERE status='OPEN'` 零行时不回滚已插入的 Evidence。

### 修复

`insert_evidence_as` 在事务内 `SELECT status, workspace_id FROM kernel.incidents ... FOR UPDATE`（与 `insert_verdict` 相同锁），然后：
- `CLOSED` → `INCIDENT_CLOSED`（所有 actor）；
- `CONCLUDED` + `AUTOMATION` → `INCIDENT_ALREADY_CONCLUDED`；
- 人工 Evidence 在 CONCLUDED 后仍允许（`afterVerdict=true`，既有契约）。

锁顺序统一为 incident → evidence；`insert_verdict` 不取 job 锁，无环。Evidence 上限检查也在同一把锁下，成为精确上限。

### 回归

- `automation_evidence_cannot_commit_after_a_human_verdict`（修复后拒绝、零行）
- `a_verdict_and_automation_evidence_serialize_without_a_missing_snapshot`（20 次真实并发；成功的 verdict 必然 `considered_evidence_count=1`；先锁的 verdict 必须 `INCIDENT_EVIDENCE_REQUIRED`，绝不出现“成功但快照缺失”）
- 既有 `a_concluded_incident_still_returns_an_effect_that_already_committed` 仍通过：已提交 effect 可被恢复返回，不新增行。

## 3. Phase 2 — Lease 与 Effect 一致性

### Finding A：过期 lease 仍有终态提交权（CONFIRMED → FIXED）

原终态 CAS：`job_id + lease_id + fencing_token + status='RUNNING'`，不含 `lease_until > now()`。A Claim → lease 过期 → 无 B 接管 → A `finish_success`/`finish_error` 仍可写终态。

修复：`finish_success` 与 `finish_error`（含 RETRY_WAIT / FAILED_FINAL）的数据库原子条件都增加 `lease_until > now()`。过期但未被接管的 job 保持 RUNNING，下一次 claim 推进 fence 后合法完成；`an_expired_lease_cannot_write_a_terminal_state_without_a_takeover` 覆盖（先拒绝，再接管 SUCCEEDED）。业务契约：**lease 过期即失去执行权，除非新 generation 重新 claim**。

### Finding B：旧 Worker 可创建 Evidence effect（CONFIRMED → FIXED）

B1.6 的 `automation_job_id` 唯一约束只保证“一 Job 一条 Evidence”，不保证写入者仍持租约。A Claim → 在 Evidence 写入前暂停 → lease 过期 / B 接管 → A 恢复并插入 Evidence：A 可能成为 effect 胜出者，B 复用 A 的 Evidence 并在自己的成功审计下结束。

修复：
- `AutomationLeaseHandle { job_id, lease_id, fencing_token }` 是内部句柄，由 worker 从 claim 结果构造，经 `collect_and_append` 传到 `append_automation_evidence`；客户端 header/body 无法伪造。
- Evidence 事务先 `SELECT ... FROM kernel.automation_jobs WHERE job_id=$1 AND lease_id=$2 AND fencing_token=$3 AND status='RUNNING' AND lease_until > now() FOR UPDATE`；不匹配 → `AUTOMATION_STALE_LEASE`，不写 Evidence、不写审计。
- 锁顺序 job → incident；`finish_success`/claim/reaper 取 job 锁，verdict 取 incident 锁，无 incident → job 路径，无死锁。
- 恢复路径仍先查 effect receipt，合法新 Worker 复用已提交 Evidence、不重复 RPC；旧 Worker 的 receipt 读取不写任何数据，随后 `finish_success` 会被 lease 条件拒绝。

回归：
- `an_expired_lease_cannot_create_an_evidence_effect`
- `a_superseded_worker_cannot_create_the_effect_but_the_new_one_can`（旧 generation 拒绝、新 generation 成功、仅一行）
- `old_and_new_generations_racing_write_one_effect`（并发，旧拒绝、新胜出、一行）
- `a_restarted_worker_recovers_a_committed_effect_without_collecting_again`（receipt 恢复 + 新 lease 终态）
- 既有 10 项 fencing/故障注入全部仍通过。

## 4. 状态机（Phase 5.1）

```
PENDING/RETRY_WAIT --claim(job lock, fence++, lease_id)--> RUNNING
RUNNING --evidence tx(job lock + live lease, incident lock, status)--> Evidence(unique job) + audit
RUNNING --finish_success(live lease, fence)--> SUCCEEDED + audit
RUNNING --finish_error(live lease, fence)--> RETRY_WAIT | FAILED_FINAL + audit
PENDING/RETRY_WAIT/expired RUNNING --reap_exhausted(attempts>=max)--> FAILED_FINAL + audit
```
Evidence、终态与各自审计同事务；旧 generation 在任何一步都被数据库条件拒绝。
