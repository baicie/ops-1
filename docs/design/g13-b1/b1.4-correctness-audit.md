### 2.2 所有权模型（修复后）

- **队列是一个状态，不是第二张表**：`origin='AUTOMATION' AND owner=服务账号 AND status IN ('OPEN','INVESTIGATING')`。迁移 0031 只增加该状态的部分索引，因此队列行不可能与 Incident 行不一致。
- **读取边界**：队列查询 `workspace_id = ANY(caller.workspaces)`；成员关系每次请求解析（`DataScope::resolve`）。Workspace B 的 Operator 既看不到也认领不了 A 的行（404，不确认存在性）。同时属于 A、B 的 Operator 可以认领两边。
- **写入边界**：认领是 `SELECT ... FOR UPDATE` + `UPDATE ... WHERE owner=服务账号 AND status IN (...) AND revision=$expected`。双人并发由行锁串行化：只有一个提交，另一个得到 `409 INCIDENT_CLAIM_TAKEN`。重复认领（同一 Operator，网络重试/双击）幂等返回已认领记录，不写第二条审计。
- **生命周期**：只有 `OPEN`/`INVESTIGATING` 可认领；`CONCLUDED`/`CLOSED` 返回 `INCIDENT_CLAIM_NOT_AVAILABLE`/`INCIDENT_RELEASE_NOT_AVAILABLE`。认领后 Evidence → Verdict → Close 走原有路径，`INCIDENT_VERDICT_WRITE_ONCE`、`CONCLUDED→CLOSED` 触发器不变。
- **权限收敛**：Viewer 在 handler 第一行被 `require_operator` 拒绝（403），任何行都未读取；人工 Incident 永远不会出现在队列，也不能通过 claim 路由探测（404）。
- **审计**：成功 `INCIDENT_CLAIMED`/`INCIDENT_RELEASED` 与被拒绝的 `INCIDENT_CLAIM_REFUSED`（TAKEN / CONFLICT / NOT_AVAILABLE）都写入 `kernel.audit_events`。成功审计与所有权变更同事务；拒绝审计在回滚后单独写入，写失败则请求失败。
- **不扩大普通读取**：`RowRule` 未改；Operator 的 `/api/v1/incidents` 仍然只返回自己拥有的行。未认领的自动 Incident 只出现在 `/api/v1/incidents/claimable` 的最小摘要中。

## 3. B1.5 — Automation Worker Lease Fencing

| 项 | 内容 |
|---|---|
| 源码位置 | `automation_worker.rs:44-69`（claim 只改 `lease_owner/lease_until`）；`:71-124`（`finish_success`/`finish_error` 只用 `job_id` UPDATE）；迁移 `0030`（无 fencing 列） |
| 当前不变量 | 租约 60 秒；过期 `RUNNING` 可被任意 Worker 重新 claim；终态写入不校验写入者是否仍持有租约。 |
| 失败场景 | A claim → A 阻塞超过 60s → B claim（同一 job）→ B 成功写 Evidence 与 `SUCCEEDED` → A 恢复，`finish_success`/`finish_error` 用 job_id 覆盖：`SUCCEEDED` 被改成 `FAILED_FINAL`，或 evidence_id 被 A 的旧结果覆盖。 |
| 复现方法 | `automation_worker::fencing_tests`（真实 PostgreSQL）：A claim → 手工把 `lease_until` 推到过去 → B claim → B `finish_success` → A 晚到 `finish_success`/`finish_error`。 |
| 实测结果 | 修复前 `automation_worker::fencing_tests::repro_a_stale_worker_overwrites_the_new_workers_result` 通过（断言 A 覆盖了 B 的 evidence；A 的晚到失败把 `SUCCEEDED` 改成 `RETRY_WAIT`）。修复后同名语义的回归测试 `a_stale_worker_cannot_overwrite_the_new_workers_result`：A 的两次写入都返回 `AUTOMATION_STALE_LEASE`，终态与 Evidence 保持 B 的结果。 |
| 修复 | 迁移 `0032_automation_job_lease_fencing.sql`：`fencing_token`（每次 claim 单调 +1）与 `lease_id`（每次 claim 新 uuid），RUNNING 必须有 lease_id、终态不得残留 lease；`claim` 的 `attempts < max_attempts` + `reap_exhausted` 保证不存在永久 RUNNING；`finish_success`/`finish_error` 在同一事务内以 `(job_id, lease_id, fencing_token, status='RUNNING')` CAS，审计失败回滚终态；重复的同一成功回执幂等；租约长度按 `2 × request_timeout + 30s` 计算并夹在 60–300s。 |
| 回归测试 | `one_worker_completes_and_a_replay_of_its_own_success_is_idempotent`、`a_stale_worker_cannot_overwrite_the_new_workers_result`、`two_workers_claiming_the_same_instant_have_one_winner`、`a_live_lease_cannot_be_claimed_by_a_second_worker`、`a_retry_clears_the_lease_and_the_next_claim_advances_the_fence`、`exhausted_jobs_are_reaped_instead_of_staying_running_forever`、`a_failed_audit_rolls_the_terminal_state_back`、`a_database_failure_does_not_report_a_terminal_state`、`many_workers_leave_no_job_unclaimed_or_permanently_running`（16 Job × 4 Worker）。 |
| 风险等级 | P1（错误终态覆盖、审计与 Evidence 不一致） |
| 状态 | **CONFIRMED → FIXED**（真实 PostgreSQL 10/10 fencing 测试通过） |

## 4. B1.6 — Evidence Exactly-once Effect

| 项 | 内容 |
|---|---|
| 源码位置 | `automation_flow.rs:301-364`（collect → attestation → `append_automation_evidence`）；`automation_worker.rs:185-198`（Evidence 写入与 `finish_success` 分两个事务）；`incident_evidence` 唯一键 `(incident_id,kind,source,content_ref)`（0016） |

| 状态 | **NEEDS_RUNTIME**（B1.6 切片先写 ADR，再做故障注入） |

## 5. B1.7 — Event 并发去重与 Principal 生命周期

### 5.1 Event 并发

| 项 | 内容 |
|---|---|
| 源码位置 | `telemetry_events.rs:260-309`（`SELECT active` 后 `INSERT`）；`0028` 的 `incidents_workspace_source_native_idx` 只覆盖 `status IN ('OPEN','INVESTIGATING','CONCLUDED')` |
| 当前不变量 | 同一 `Idempotency-Key` 由 `telemetry_events` 唯一键兜底；同一 `(workspace, source, nativeId)` 的 Active Incident 由部分唯一索引兜底。 |
| 失败场景 | 两个**不同** Event Key（不同 `trigger_state`/`occurred_at` 导致 key 不同）并发提交同一 `nativeId`：两个事务都 SELECT 不到 active，都 INSERT；唯一索引让一个失败，但 `store_event` 没有 `ON CONFLICT`/重试映射，原始 DB 唯一错误冒泡为 500，且该 Event 没有关联到胜出的 Incident。乱序 PROBLEM/RESOLVED、CLOSED 后新 PROBLEM 需要明确语义。 |
| 风险等级 | P1（500 + Event 丢失关联；并发下语义不稳定） |
| 状态 | **NEEDS_RUNTIME**（B1.7 切片做真实 32/64 并发测试） |

| 项 | 内容 |

## 6. 被证伪的怀疑

| 怀疑 | 结论 | 依据 |
|---|---|---|
| “自动化 Incident 没有 owner，导致 Operator 看不到” | REFUTED | 有 owner，是服务账号；问题是 owner 与 Operator 行规则不相交。 |
| “`append_automation_evidence` 允许自动化写 CONCLUDED Incident” | REFUTED | `incidents.rs:697-711` 明确拒绝 `CONCLUDED` 与 `CLOSED`。 |
| “Worker 没有重试上限” | REFUTED | `max_attempts` 3，`finish_error` 有 `job.attempts < max_attempts` 与退避。 |
| “Event 幂等键允许重复 Event 创建第二个 Incident” | 已由既有测试覆盖 | `duplicate_event_creates_one_incident_and_resolved_creates_none`：同 key 重试返回原 incident。不同 key 的并发才是有问题的分支（§5.1）。 |

## 7. 新发现（随切片推进补充）

- B1.5 的复现测试同时会暴露：`finish_success`/`finish_error` 的审计在状态更新之后用 `let _ =` 忽略失败（`automation_worker.rs:82, 125`），与 AGENTS.md“关键审计不得静默失败”冲突。修复时与终态写入同事务。
- `automation_worker.rs` 的 `claim` 不区分 `PENDING`/`RETRY_WAIT` 已超过 `max_attempts` 的僵尸行；修复时在 claim 谓词里排除并将超限行收敛到 `FAILED_FINAL`。
