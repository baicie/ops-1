# ADR-G13-B1.6 — Evidence Exactly-once Effect for Automation Jobs

- 日期：2026-11-08
- 基线：`main` `0112f7e` + stacked B1.4/B1.5 分支
- 状态：Accepted（实现于 `fix/g13-b1-evidence-exactly-once`，迁移 `0033`）
- 相关：ADR-019（Event 身份）、B1.3（durable job）、B1.5（lease fencing）、
  `docs/design/g12-evidence/evidence-content-adr.md`、`docs/design/g11-incident/incident-adr.md`

## 1. 问题

B1.3 的执行顺序是：

```
claim(job) -> collect (RPC) -> attestation (RPC) -> INSERT evidence (tx) -> finish_success (tx)
```

Evidence 与 Job 终态是两个事务。故障窗口：

1. Evidence 已提交；
2. Job 仍是 RUNNING；
3. 进程崩溃，租约过期，另一个 Worker 重试；
4. 重新 collect 的时间窗口/采样不同 → 新的 `contentRef`；
5. `incident_evidence` 的唯一键是 `(incident_id, kind, source, content_ref)`，
   新 tuple 不冲突 → 第二条 Evidence。

现有唯一键只保证“相同内容不重复”，不保证“同一 Job 的逻辑副作用至多提交一次”。
Human Verdict 冻结的是签署时读到的证据集合；第二条 Evidence 会以 `afterVerdict`
出现，并可能诱导后续复核，尽管它只是同一次采集的重复副作用。

## 2. 明确区分的四种语义

| 语义 | 保证 | 说明 |
|---|---|---|
| Event ingestion | Exactly-once 逻辑摄入 | `telemetry_events` 唯一键 `(workspace, source, idempotency_key)`；重试返回原 Event/Incident/Job。 |
| Job 执行 | At-least-once | 租约过期会重试；`attempts` 有上限。 |
| Evidence 逻辑副作用 | **Exactly-once（本 ADR 的核心）** | 同一 `job_id` 至多绑定一条最终 Evidence；重复执行复用已提交结果。 |
| 外部 Zabbix RPC | At-most / at-least-once，**不保证 Exactly-once** | 崩溃发生在 RPC 之后、Evidence 之前时，重试会再次调用 Zabbix。采集是只读操作，重复调用不改变上游状态；但次数不可精确控制，本文与代码都不宣称 RPC Exactly-once。 |

## 3. 决策

### 3.1 Effect Identity：Job 是副作用的身份

`kernel.incident_evidence` 增加 `automation_job_id uuid`，并建立部分唯一索引：

```sql
CREATE UNIQUE INDEX incident_evidence_job_key
    ON kernel.incident_evidence (automation_job_id)
    WHERE automation_job_id IS NOT NULL;
```

Evidence 行本身是 Effect Receipt。写入 Evidence 的 `INSERT` 同时写入 `automation_job_id`，
因此“Evidence 已提交”与“receipt 已提交”是同一个原子事实，不存在二者之间的窗口。
不引入第二张 receipt 表：第二张表会允许“Evidence 存在但 receipt 不存在”，而这正是要消除的窗口。

### 3.2 唯一键的分层

- **Job-scoped 行**（`automation_job_id IS NOT NULL`）：唯一身份是 `automation_job_id`。
  两个不同 Job 即使产生完全相同的 `(incident, kind, source, contentRef)`，也必须是两行：
  它们代表两次独立采集，合并不等于去重，而是丢失一次副作用的归属。
- **非 Job-scoped 行**（人工提交、历史自动化行）：保留 0016 的
  `(incident_id, kind, source, content_ref)` 唯一键。迁移把表级 UNIQUE 约束替换为
  同列的部分唯一索引 `WHERE automation_job_id IS NULL`，历史行（全为 NULL）行为不变。

### 3.3 提交协议

一次 attempt：

1. **先查 receipt**：`SELECT evidence_id FROM kernel.incident_evidence WHERE automation_job_id = $job`。
   命中 → 不调用任何 RPC，直接 `finish_success(job, evidence_id)`（仍需 B1.5 的
   lease/fence CAS）。
2. 未命中 → collect → attestation → 校验签名/内容上限。
3. `INSERT evidence (…, automation_job_id=$job) ON CONFLICT (automation_job_id)
   WHERE automation_job_id IS NOT NULL DO NOTHING RETURNING evidence_id`。
   - 插入成功：Evidence + content + incident OPEN→INVESTIGATING + audit 在同一事务提交。
   - 冲突：另一个 attempt 已提交该 Job 的唯一 Evidence；读取并返回它，不写第二条。
4. `finish_success`（B1.5 fencing）。

第 3 步的冲突处理是“同 Job 重复执行返回已提交结果”的实现；第 1 步是恢复路径，
避免盲目重采。两者都不修改已提交的 Evidence 原文、内容 digest、attestation 或
Human Verdict 的证据快照。

### 3.4 恢复语义与故障矩阵

| 崩溃点 | 数据库状态 | 重试行为 | 结果 |
|---|---|---|---|
| Collect 前 | Job RUNNING/租约过期，无 Evidence | 重新 claim，正常 collect | 一次 Evidence |
| Collect 成功、Attestation 前 | 同上（RPC 已发生，无落库） | 重新 collect（RPC 第二次） | 一次 Evidence；RPC ≥1 次 |
| Attestation 成功后、Evidence 前 | RPC 已返回，无落库 | 重新 collect/attest | 一次 Evidence；RPC ≥1 次 |
| Evidence INSERT 事务内 | 事务回滚 | 重新执行 | 一次 Evidence |
| Evidence 提交后、Job Success 前 | Evidence 有 `automation_job_id`，Job RUNNING | 第 1 步命中 receipt → 不再 RPC → finish_success | 一次 Evidence |
| Job Success 提交后、Worker 返回前 | Job SUCCEEDED | 不再 claim（终态） | 一次 Evidence |
| 重复 Event | Event 唯一键命中 | 返回原 job | 一个 Job、一次 Evidence |
| 双 Worker 竞争同一 Job | 一个当前 fence | 旧 Worker 的 Evidence INSERT 若先到，成为唯一行；新 Worker 命中 receipt；终态写入由 B1.5 fence 决定 | 一次 Evidence |
| 执行期间 Incident 被 Human Verdict 结束 | Evidence 已提交或未提交 | 未提交 → `append_automation_evidence` 拒绝（INCIDENT_ALREADY_CONCLUDED），Job FAILED_FINAL；已提交 → 恢复命中，记录 SUCCEEDED（副作用已存在） | 不新增 Evidence、不重解释裁决 |

### 3.5 审计与状态

- Evidence 事务内的 `INCIDENT_EVIDENCE_ADDED` 审计保持原样（actor AUTOMATION）。
- 恢复路径不重复写 Evidence 审计；`finish_success` 写一次
  `telemetry.automation.succeeded`（B1.5 已保证与终态同事务）。
- 冲突读取到既有 Evidence 时，返回的 `AutomationRunView.evidence_id` 是已提交行的 id；
  调用方可据此确认“这次执行复用了既有副作用”。

### 3.6 为什么不选择其他方案

- **第二张 effect receipt 表 + 两阶段提交**：需要跨两个事务协调，崩溃窗口仍在；
  若 receipt 先行，必须处理“receipt 有、Evidence 无”的悬挂引用。Evidence 自身承载
  job_id 更简单且可证明。
- **把 contentRef 改成 job 作用域**：attestation 的签名覆盖 `contentRef`，改动会使
  插件签名无法验证；等于让 Kernel 重解释已签声明，违反“已签 Attestation 不得重解释”。
- **删除/覆盖旧 Evidence**：违反 Evidence 不可篡改与 Human Verdict 快照不变。
- **禁用重试**：把可恢复故障变成永久失败，违反 B1.3 的持久任务语义。

## 4. 兼容性

- `automation_job_id` 可空；历史 Evidence 全为 NULL，继续由原 tuple 唯一索引保护。
- 迁移不重写任何 Evidence 内容、digest、trust、attestation 或 verdict 快照。
- 0016 的 UNIQUE 约束被替换为等价的部分唯一索引（`WHERE automation_job_id IS NULL`）；
  对既有行的约束效果相同。
- Rollback（破坏性仅限新列/索引；已有 Evidence 不删除）：
  ```sql
  DROP INDEX kernel.incident_evidence_job_key;
  DROP INDEX kernel.incident_evidence_content_key;
  ALTER TABLE kernel.incident_evidence DROP COLUMN automation_job_id;
  ALTER TABLE kernel.incident_evidence
      ADD CONSTRAINT incident_evidence_incident_id_kind_source_content_ref_key
      UNIQUE (incident_id, kind, source, content_ref);
  ```
  回滚会重新允许“不同 Job 相同内容合并”的旧行为，且需要先确认没有两行相同 tuple 的
  Job-scoped 数据；因此不是无代价回滚。

## 5. 验收不变量

1. 同一 `job_id` 至多一条 Evidence（数据库唯一索引）。
2. 同一 Job 的重复执行返回同一 `evidence_id`，不新增 Evidence、不改写内容。
3. 恢复先查 receipt，不盲目重采（可用“无可用 Node/插件时仍成功”证明）。
4. 不同 Job 相同内容不合并。
5. Evidence 原文、content digest、attestation、Human Verdict 快照均不被修改。
6. 外部 RPC 次数不宣称 Exactly-once；文档、日志与测试均按 at-least-once 描述。
