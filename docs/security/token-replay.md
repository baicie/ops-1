# Token 重放：当前行为与未决策的空白

**核实 2026-11-20，main `d6f3117`。TASK-25 点名「token replay 没有 HTTP 级负例」——核实结果比那更基本。**

---

## 1. 结论：重放没有被防护，且没有记录这是不是有意

| Token 类型 | 过期 | 重放防护 |
|---|---|---|
| workload token (`oww1`) | **强制**（`capabilities.rs:1213`） | **无** |
| automation principal | 一次性消耗（`automation.rs:154`，`AUTOMATION_REPLAY`） | **有** |

`WorkloadClaims` 有 `jti` 字段（`capabilities.rs:90`），每次签发都生成新的
（`:346`、`:454`）——但**全仓库没有任何地方检查它是否被用过**。

**所以 workload token 在一个 TTL（默认 3600 秒）内可以被无限次重放。**

## 2. 这是缺陷还是设计？

**无法从代码判断，因为没有任何注释、ADR 或测试说明哪个是意图。**

两种读法都成立：

- **设计**：无状态 token 的标准权衡。检查 `jti` 需要一个有状态的消耗表，每次请求一次写，
  对一个高频的内部调用路径是显著成本。TTL 短且 token 只能由一个插件持有（按签名密钥隔离），
  重放窗口被这两个条件限制。
- **缺陷**：`jti` **存在**。一个不打算检查的字段通常不会生成。生成一个随机唯一 id
  只为了丢弃它，是「计划过但没做完」的样子。

**我不替它做决定。** 记 `NEEDS_DECISION`，代价如下。

## 3. 如果要防护，代价是什么

| 方案 | 代价 |
|---|---|
| `jti` 消耗表 | 每次使用一次 INSERT + 冲突检查；表按 TTL 增长需清理；对高频路径是新的写热点 |
| 非重放的不透明 token | 与现在的签名 token 完全不同，签发与验证两侧都要改 |
| 缩短 TTL | 不消除重放，只缩小窗口；增加刷新频率 |

**没有一个是不花代价的**，所以「加个 jti 检查」不是一行代码的事。

## 4. 为什么没写测试

能断言的只有「同一个 token 两次都成功」。那样的测试不是安全属性，是**行为快照**——
而且容易被读成「重放是可接受的」。

**一个看起来像背书的测试比一个记录在案的空白更糟。** 所以记在这里，不写进测试。

## 5. 有真实防护的那一条

`automation_principal_uses` 用 `INSERT ... ON CONFLICT DO NOTHING` 做一次性消耗，
冲突即 `AUTOMATION_REPLAY`（`automation.rs:148-160`），并有单元测试断言。

**这是真正的防重放，且只覆盖 automation principal。** 把它当作全平台的属性是错的。
